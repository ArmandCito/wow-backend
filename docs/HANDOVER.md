## 1. What changed, and why

| Before | Now | Why |
|---|---|---|
| Auth and menu only; orders, payments, promotions, dashboard empty | **Every domain of the contract**: auth, catalogue, checkout, client orders, notifications, register, menu editing, uploads, campaigns, business settings, staff admin, overview, audit | Everything the website needs to replace its mock data |
| `/accounts/login/`, `/menu/items/{id}/`… | Contract paths: `/auth/sign-in`, `/menu/items/{slug}`… (mapping in section 8) | The website is built on these paths |
| `snake_case` JSON | `camelCase` JSON (Python stays snake_case) | Same names as the website's TypeScript types |
| Errors as `{"detail": …}` or `{"error": "…"}` | One format: `{"error": {"code", "message", "details"}}`, validation errors as 422 | The website translates stable codes (EN/FR) |
| Login body without `user`, no `/me` | Every sign-in returns `{access, refresh, user}`; `GET /auth/me` returns role, permissions, client code, grant | The website routes people by role and permission |
| Roles `owner/manager/customer` | `superadmin/manager/client` | Contract names |
| User created inactive at sign-up, 5-digit OTP | **Pending sign-up**: the account exists only after the **6-digit** code | An unverified email no longer blocks a real sign-up; same as the website |
| `django-parler` + one language per response (`?lang=`) | Two columns per text (`name_en`, `name_fr`), the API returns `{"en", "fr"}`. DeepL kept, optional, to fill an empty language | The website shows both languages from one response |
| Integer ids, no price on items, prices as decimal strings | Slugs (`wow-toasted-burger`), `price` integer RWF on the item, option groups (add/remove, required, max) | Product URLs, cart and checkout of the website |
| Variants | Removed: model sizes as a **required option group** (e.g. "Size", max 1) | The website has no variants; option groups cover the case |
| `django-allauth` | Removed (Google OAuth is done by the website, which calls `POST /auth/google`) | Less to maintain |
| Brevo called inside the views | A Django email backend (`core/mail.py`): the code uses `send_mail()` | Console emails in development, testable |
| Database required to start | SQLite when no database is configured | Quick local start and tests |
| 2 test files | **37 tests** covering every domain | Safe changes |

What we kept from your work: Django 5.2 + DRF + Simple JWT + drf-spectacular, Render + Neon, Brevo,
DeepL, rate limiting, blacklisting refresh tokens on sign-out, the audit idea (append-only), the
temporary content grants of managers, soft-deleted menu items.

## 2. Deploy, step by step

### 2.1 Reset the Neon database (once)

The migrations start again from `0001_initial`. The tables of the previous version do not match, and
Django would believe some migrations are already applied. **Before the first deploy**, empty the
database (it only holds test data: the menu was empty).

In the Neon console → SQL Editor, on the database used by Render:

```sql
DROP SCHEMA public CASCADE;
CREATE SCHEMA public;
```

(Or create a new Neon database/branch and use its connection string.)

### 2.2 Push the code

Commit this folder on your repository (`Solvit-Africa-Training-Center/Wow-quick-bites_Backend`), on a
new branch first (e.g. `feat/contract-api`), then merge into the branch Render deploys. `.env`, `.venv`,
`db.sqlite3` and `media/` are ignored by git.

### 2.3 Environment variables on Render

Dashboard → the service → Environment. `render.yaml` declares them all.

| Variable | Required | Value |
|---|---|---|
| `DATABASE_URL` | **yes** | Neon *pooled* connection string, with `?sslmode=require` |
| `SECRET_KEY` | **yes** | Generated by the Blueprint, or any long random string |
| `DEBUG` | | `False` |
| `ALLOWED_HOSTS` | | `.onrender.com` |
| `CSRF_TRUSTED_ORIGINS` | for `/admin/` | `https://wow-quick-bites-backend-ziwt.onrender.com` |
| `FRONTEND_URL` | **yes** | `https://wow-quick-bites-ui.vercel.app` (set by `render.yaml`; no trailing slash). Used in reset and invitation emails. |
| `FRONTEND_SHARED_SECRET` | **yes** | Long random string. **Send it privately to the frontend team** (not in the group chat). |
| `BREVO_API_KEY`, `BREVO_SENDER_EMAIL` | **yes** | Your Brevo key and a sender verified in Brevo. Without them, emails only go to the log. |
| `SUPERADMIN_EMAIL`, `SUPERADMIN_PASSWORD`, `SUPERADMIN_NAME` | first deploy | The owner's account, created at deploy if missing (never overwritten). |
| `CLOUDINARY_URL` | recommended | `cloudinary://<key>:<secret>@<cloud>`. Without it, uploaded photos are stored on Render's disk, **which is wiped at every deploy**. |
| `DEEPL_AUTH_KEY` | optional | Fills the language an editor left empty. |
| `PYTHON_VERSION` | | `3.13.5` (set by `render.yaml`) |

Generate a secret: `python -c "import secrets; print(secrets.token_urlsafe(48))"`.

### 2.4 What the build does

`render.yaml` runs, on every deploy (each step is safe to repeat):

1. `pip install -r requirements.txt`
2. `collectstatic` (Django admin styles)
3. `migrate`
4. `seed --if-empty`: loads the website's menu (30 items, categories, option groups, tags), the 3
   homepage promotions and the business details — **only if the menu is empty**, so portal edits are
   never overwritten.
5. `ensure_superadmin`: creates the owner from `SUPERADMIN_*` if missing.

If the service was created without the Blueprint, copy the build and start commands from `render.yaml`.

## 3. Run it locally

```bash
python -m venv .venv
.venv\Scripts\activate            # macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
copy .env.example .env            # macOS/Linux: cp .env.example .env  (then edit)
python manage.py migrate
python manage.py seed --demo-accounts
python manage.py runserver
```

- No `DATABASE_URL` and no `DB_NAME` → SQLite (`db.sqlite3`). Your current `.env` (DB_NAME…, Brevo,
  DeepL) still works: the variable names did not change. **Your `.env` was not modified.**
- No `BREVO_API_KEY` → emails (codes, links) are printed in the terminal.
- The `SECRET_KEY` of your current `.env` is short (18 characters): replace it with a long random value
  (`python -c "import secrets; print(secrets.token_urlsafe(48))"`).
- Open http://127.0.0.1:8000/api/docs/.

Tests (SQLite, no external service): `python manage.py test` → 37 tests.

## 4. Tour of the code

One Django app per area of the contract. Each app has the same files:

| File | Role |
|---|---|
| `models.py` | Tables |
| `serializers.py` | JSON in and out (validation) |
| `services.py` | **The business rules** (one function per use case). Views never contain rules. |
| `views.py` | HTTP: permissions, calls a service, shapes the response, Swagger description |
| `urls.py` | Paths (optional trailing slash via `core.routing.route`) |
| `tests.py` | API tests |

| App | Content |
|---|---|
| `core` | Shared pieces: error format (`errors.py`, `exceptions.py`), bilingual field (`fields.py`), Rwandan phone (`phone.py`), emails (`emails.py`, `mail.py`), rate limits (`throttles.py`), uploads, Kigali time, `seed` and `ensure_superadmin` commands, seed data (`seed/catalogue.json`), test helpers (`testing.py`) |
| `accounts` | Users, pending sign-ups, one-time links, content grants, **permissions (`access.py`)**, JWT authentication, auth endpoints |
| `menu` | Categories, drink sections, tags, option groups, items; public catalogue and portal editing |
| `orders` | Orders and lines (price snapshots), checkout, register, assignment |
| `notifications` | Client notifications (texts in EN/FR) |
| `promotions` | Homepage campaigns |
| `business` | Business details and fees (one row) |
| `staff` | Managers, invitations, grants, overview |
| `audit` | Append-only audit trail and `record()` |
| `WOWBites` | Settings and root URLs |

### Adding an endpoint

1. Business rule in `services.py` (raise errors from `core/errors.py`: never build error JSON by hand).
2. Serializer for the input/output.
3. View: `permission_classes = [require("some:permission")]` (from `accounts/access.py`) and
   `@extend_schema(...)` so Swagger shows it.
4. Route in the app's `urls.py`.
5. A test in `tests.py`.
6. Tell the frontend team (section 5).

### Conventions to keep

- JSON camelCase (automatic), Python snake_case.
- Money in integer RWF; dates through DRF (Kigali offset).
- Public ids: slugs, `ORD-…`, client codes, staff ids. Never expose numeric ids.
- Bilingual text: `name_en` / `name_fr` columns + `LocalizedField` in serializers.
- New error → a class in `core/errors.py` with a new stable `code`, listed in `docs/API.md`.

## 7. Security notes

- `DEBUG=False` in production (required, the app refuses to start without `SECRET_KEY`).
- Passwords: Django's PBKDF2 hashing and validators (8+ characters, not common, not only digits).
- Email codes and link tokens are stored **hashed**; links are single-use and expire.
- Sign-in, code resend and password reset never reveal whether an email has an account. Sign-up does
  (`409 email_taken`), as the contract requires.
- Suspension blocks the account at once and revokes its refresh tokens.
- `POST /auth/google` trusts only calls carrying `FRONTEND_SHARED_SECRET`.
- Uploaded images are re-encoded (metadata removed), 5 MB max, JPEG/PNG/WebP only.
